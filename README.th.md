# V2 — ESP32-CAM: เห็นกรวย → หากึ่งกลางเลน → ขับเอง

จุดเริ่มต้นใหม่ของโปรเจกต์: ESP32-CAM ถ่าย → ส่งมาที่เครื่อง → แสดงผล → (ถ้าเปิด) หากรวยสีฟ้าในภาพ
สายงานเต็ม: `วิดีโอ → cone_detection → lane_center → autopilot → robot_link → มอเตอร์`
แต่ละขั้นแยกไฟล์และทดสอบเดี่ยวได้ ขั้นที่ขยับรถจริงมีแค่ `autodrive.py` ไฟล์เดียว

## ไฟล์

| ไฟล์ | หน้าที่ |
| --- | --- |
| `run.py` | **เริ่มที่นี่** คำสั่งเดียว: หากล้องในวง LAN → ตั้งความละเอียด → เปิดสตรีม → โชว์ภาพสด |
| `cone_detection.py` | หากรวย**สีฟ้า** จากสี + รูปร่าง (`ConeDetector.detect()`) รันเดี่ยวเพื่อจูนก็ได้ |
| `lane_center.py` | หาจุดกึ่งกลางระหว่างกรวยซ้าย-ขวา (`LaneFinder.update()`) |
| `autopilot.py` | แปลงค่าเบี่ยง → พวงมาลัย/คันเร่ง (P-controller) ไฟล์เดียวที่ตัดสินใจว่ารถจะขยับยังไง |
| `robot_link.py` | ส่งคำสั่ง UDP ไปบอร์ด (แกะมาจาก `Aj-Piya_code/2026_07_13.py`) |
| `autodrive.py` | **ตัวที่ขับรถจริง** รวมทุกขั้นเข้าด้วยกัน |
| `firmware/esp32cam_robot/` | เฟิร์มแวร์หุ่นยนต์ ตัวเดียวที่คุมมอเตอร์ได้ |
| `cone_config.json` | ค่า HSV, ตัวกรอง, และค่าของ lane ที่จูนไว้ |
| `camera_control.py` | ตั้ง resolution/quality/flip + **ล็อก AWB/exposure** ผ่าน `/control` |
| `esp32_link_check.py` | ตรวจลิงก์ UDP กับเฟิร์มแวร์หุ่นยนต์ แล้วบอกว่าพังตรงไหน (ใช้ตอนไม่มีภาพเข้ามาเลย) |
| `link_monitor.py` | เฝ้าวัดลิงก์ MJPEG เป็นสิบๆ นาที แล้วสรุปว่าอะไรค่อยๆ แย่ลง: เซ็นเซอร์ / วิทยุ / heap / รีบูต / PC |
| `camera_setup.py` | ขั้นตอนก่อนเปิดสตรีม: สแกนหากล้อง → ตั้งความละเอียด → ล็อก AWB → พลิกภาพ ใช้ร่วมกันทั้ง `run.py` และ `autodrive.py` |
| `mjpeg_video_source.py` | รับ `http://<ip>:81/stream` จาก CameraWebServer (thread แยก เก็บเฉพาะเฟรมล่าสุด ต่อใหม่เองได้) |
| `esp32_video_source.py` | รับ UDP จาก `sketch_jul13a.ino` (เฟิร์มแวร์หุ่นยนต์) |
| `video_source.py` | เลือกตัวรับตาม `--source` (`webserver` / `esp32` / URL `http://`) |
| `capture_esp32_samples.py` | เซฟเฟรมจากสตรีมเป็น `.jpg` ไว้ทดสอบออฟไลน์ |
| `CameraWebServer/` | เฟิร์มแวร์ที่ใช้อยู่ (MJPEG over HTTP) |

ตัวรับทั้งสองแบบคืน **เฟรม BGR** เหมือนกัน (`src.get_frame()`) เลยต่อโค้ดอะไรทับก็ได้โดยไม่ต้องสนว่าเฟิร์มแวร์ไหนอยู่ข้างล่าง

## รัน

```
cd V2
python run.py                          # หากล้องเอง
python run.py --esp-ip 192.168.8.191   # รู้ IP แล้ว ข้ามการสแกน
python run.py --source esp32           # ใช้เส้นทางสำรอง UDP (เฟิร์มแวร์หุ่นยนต์เท่านั้น)
python run.py --framesize qvga         # เล็กลง เร็วขึ้น
python run.py --flip both              # กล้องติดกลับหัว
python run.py --detect                 # เปิดการตรวจจับกรวย + แถบจูน HSV
```

ในหน้าต่างภาพ: กด `v` พลิกบน-ล่าง, `h` พลิกซ้าย-ขวา, `s` เซฟเฟรมลง `./esp32_samples/`, `w` เขียนค่าที่จูน (เฉพาะ `--detect`), `q` ออก
มุมบนซ้ายบอกความละเอียด / fps / สถานะ flip / จำนวนที่เซฟไปแล้ว

### เรื่อง flip

`--flip` มี `none` (ค่าเริ่มต้น) / `v` (บน-ล่าง) / `h` (ซ้าย-ขวา) / `both` (กลับหัว)

ถ้าใช้ `--source webserver` โปรแกรมจะสั่ง **พลิกที่ตัวเซนเซอร์** (`/control?var=vflip` กับ `var=hmirror`)
ดีกว่าพลิกด้วย OpenCV เพราะไม่กิน CPU ฝั่ง PC และภาพในเบราว์เซอร์ก็จะตรงกับที่ Python เห็น
ถ้ากล้องไม่ยอมรับ หรือใช้ `--source esp32` (เฟิร์มแวร์ UDP ไม่มี HTTP endpoint) จะ fallback ไปพลิกด้วย `cv2.flip` แทน — บรรทัดที่ print ตอนเริ่มบอกว่าใช้ทางไหน

ค่าที่พลิกฝังอยู่ในเซนเซอร์จนกว่ากล้องจะ reboot โปรแกรมเลย**สั่งทุกครั้งที่เปิด แม้ตอน `--flip none`** เพื่อเคลียร์ค่าที่ค้างจากรอบก่อน (ไม่งั้นจะงงว่าทำไมภาพกลับหัวทั้งที่ไม่ได้สั่ง)

ค่าเริ่มต้นเป็น **VGA (640×480)** ให้ตรงกับเฟิร์มแวร์หุ่นยนต์ (`sketch_jul13a.ino`)

เครื่องมือแยก ถ้าอยากใช้ทีละชิ้น:

```
python mjpeg_video_source.py --esp-ip 192.168.8.191    # เช็กว่าภาพมาไหม เฉยๆ
python capture_esp32_samples.py --source webserver --esp-ip 192.168.8.191
```

## เรื่องที่มักจะเจอ

- **ต่อได้ทีละคนเดียว** ESP32-CAM รับ stream client ได้แค่ 1 — ถ้าเปิดหน้าเว็บกล้องค้างไว้ในเบราว์เซอร์ Python จะไม่ได้เฟรมเลย ปิดแท็บก่อน
- **การเปลี่ยนความละเอียดไม่ถาวร** `run.py` สั่งผ่าน HTTP ทุกครั้งที่เปิด กล้อง reboot แล้วกลับเป็น QVGA ก็หายเอง ถ้าอยากให้ถาวรแก้ `FRAMESIZE_QVGA` → `FRAMESIZE_VGA` ที่ `CameraWebServer.ino:96` แล้วแฟลชใหม่
- **อย่า hardcode เลข framesize** `val` ใน `/control?var=framesize&val=N` เป็น index ดิบของ enum `framesize_t` และ core esp32 บนเครื่องนี้ (4.0.0-alpha1) แทรก `128X128` กับ `320X320` เข้าไป ทำให้ VGA = 10 ไม่ใช่ 8 ตามที่เว็บส่วนใหญ่บอก — `camera_control.py` เลยลองแล้ววัดผลจริงผ่าน `/capture` แทนที่จะเชื่อเลข
- **ภาพกระตุก = ลูปกินซีพียูจนแย่ง thread ที่รับภาพ** `get_frame()` คืนภาพเดิมซ้ำไปเรื่อยๆ ถ้าลูปประมวลผลทุกรอบโดยไม่เช็กว่าเฟรมใหม่มาหรือยัง
  มันจะรัน detection + `imshow` ~500 ครั้ง/วินาที กับภาพที่มาจริงแค่ ~20 เฟรม/วินาที → ซีพียูเต็มคอร์ → thread ที่รับ UDP ไม่ได้รัน → buffer ล้น → chunk หาย → เฟรมประกอบไม่ครบ → **กระตุก**
  บน TCP (MJPEG) อาการจะออกเป็นดีเลย์แทนที่จะกระตุก เพราะข้อมูลไม่หาย ทั้ง `run.py` และ `autodrive.py` เลยเช็ก `src.frame_count` ก่อน ถ้ายังเป็นเฟรมเดิมก็ `cv2.waitKey(5)` แล้วข้ามไป
- **MJPEG บน TCP ดีเลย์มากกว่า UDP ของหุ่นยนต์** ดูภาพเฉยๆ ไม่มีปัญหา แต่ถ้าจะปิด loop กับมอเตอร์เมื่อไหร่ให้ย้ายไป `--source esp32`
- **CameraWebServer ไม่มีระบบควบคุมมอเตอร์** ถ้าจะขับจริงต้องแฟลช `sketch_jul13a.ino` กลับไป

## การตรวจจับกรวยสีฟ้า

```
python run.py --detect                                       # ปกติใช้อันนี้
python cone_detection.py --source webserver --esp-ip <ip>    # ตรวจจับอย่างเดียว
python cone_detection.py --source esp32_samples/xxx.jpg      # จูนกับภาพที่เซฟไว้ ไม่ต้องต่อกล้อง
```

**ทำไมฟ้าไม่ใช่ส้ม** — ส้มอยู่ตรงรอยต่อ H=0/179 ต้องยิง `inRange` สองรอบ ส่วนฟ้าอยู่กลางแผง (H≈100) ยิงรอบเดียวจบ
และของที่ทำให้ตัวตรวจจับสีส้มพังในห้องจริง (สีผิวคน กล่องกระดาษ พื้นไม้ โต๊ะ) อยู่ที่ H 5–25 ทับกรวยส้มพอดี ขณะที่ในห้องแทบไม่มีอะไรฟ้าอิ่มสี

**สีอย่างเดียวไม่พอ** ทุกก้อนต้องผ่านตัวกรอง 4 ชั้นก่อนถึงจะนับเป็นกรวย

| ตัวกรอง | ตัดอะไรออก |
|---|---|
| `min/max_contour_area` | จุดรบกวนจาก JPEG กับผนัง/พื้นทั้งแผ่น |
| `min/max_aspect_ratio` (w/h 0.2–1.3) | กรวยสูงกว่ากว้าง → ตัดยีนส์ พนักเก้าอี้ จอมอนิเตอร์ |
| `min_solidity` (0.75) | ก้อนเว้าแหว่ง (พื้นที่ contour ÷ convex hull) |
| `roi_top_ratio` (0.4) | ทุกอย่างเหนือเส้นขอบฟ้า — ท้องฟ้าผ่านหน้าต่าง จอ เสื้อคน |

ROI ทำโดย**ล้าง mask ส่วนบน ไม่ใช่ crop ภาพ** พิกัดที่ได้จึงเป็นพิกัดเต็มเฟรม ไม่ต้องบวก offset กลับทีหลัง (จุดที่พลาดกันบ่อย)

**ค่าตั้งต้น** H 90–130, S≥80, V≥40 — `S min` 80 เพราะฟ้าซีดเยอะกว่าที่คิด, `V min` 40 เพราะกรวยฟ้าเข้มกว่าส้มโดยธรรมชาติ ตั้ง V สูงแบบส้มจะหลุดหมด

**`min_contour_area` เป็นพิกเซลดิบ** ผูกกับความละเอียดที่กล้องส่งมา 1500 px ≈ 0.5% ของ VGA แต่ ≈ 2% ของ QVGA — เปลี่ยน `--framesize` เมื่อไหร่ต้องจูนใหม่

### ต้องล็อก AWB ก่อนจูนเสมอ

`run.py` ล็อกให้อัตโนมัติแล้ว (ปิดด้วย `--no-lock`) auto white balance ทำงานโดยปรับ gain ของช่อง**น้ำเงิน/แดง** ตรงๆ ซึ่งเป็นแกนเดียวกับที่กรวยฟ้าอยู่ — จูน HSV ตอน AWB ยังวิ่ง = ได้ค่าที่อธิบาย "อารมณ์ของกล้องตอนนั้น" ไม่ใช่สีกรวย พอแสงเปลี่ยนก็ใช้ไม่ได้

กล้องจะค้างค่าที่ auto ปรับไว้ ณ วินาทีที่ล็อก โปรแกรมเลยรอ 2 วิให้นิ่งก่อน — **หันกล้องไปที่สนามจริงตอนนั้น** ไม่งั้นจะล็อกค่าที่ยังปรับไม่เสร็จ (ภาพจะออกเขียวหรือชมพู)

## จุดกึ่งกลางเลน

```python
from cone_detection import ConeDetector
from lane_center import LaneFinder

det = ConeDetector()
lane = LaneFinder(det.cfg)          # ใช้ config ก้อนเดียวกัน

cones, mask, debug = det.detect(frame)
r = lane.update(cones, frame.shape[1], frame.shape[0])

r.target_x      # px — กึ่งกลางช่องว่างอยู่ตรงไหน
r.offset_norm   # -1.0 (ช่องว่างอยู่ซ้ายสุด) .. +1.0 (ขวาสุด), 0 = ตรงกลางพอดี
r.state         # both / left / right / lost
r.have_target   # False = ค่าที่ได้เป็นของเก่าค้างไว้ อย่าเอาไปขับ
```

`offset_norm` คือค่าที่ตัวคุมพวงมาลัยจะกินต่อ — **ในไฟล์นี้ไม่มีตัวคุม** ไม่มี gain ไม่มีคันเร่ง ไม่มีอะไรที่ทำให้รถขยับ

### 4 เรื่องที่ทำให้มันไม่ใช่แค่ `(ซ้าย + ขวา) / 2`

**1. จะรู้ได้ยังไงว่ากรวยไหน "ซ้าย" ไหน "ขวา"** — แบ่งที่กึ่งกลางเฟรมใช้ได้เฉพาะตอนรถอยู่กลางเลนอยู่แล้ว
คือตอนที่ไม่ต้องการคำตอบ พอรถเบี่ยงมากๆ กรวยทั้งสองอันจะไปอยู่ฝั่งเดียวกัน แล้วโค้ดจะสรุปว่า "มีแต่กรวยซ้าย ไม่มีขวา" → สั่งเลี้ยวผิดทางหนักขึ้นไปอีก
แก้สองชั้น: แบ่งที่**จุดกึ่งกลางเลนที่จำไว้รอบก่อน** (ซึ่งขยับตามรถ) และถ้ายังไปกองฝั่งเดียวอยู่ ให้**แบ่งที่ช่องว่างกว้างสุดระหว่างกรวยเอง** — ซึ่งก็คือช่องที่รถต้องวิ่งผ่านนั่นแหละ ชั้นที่สองคือตัวที่ช่วยเฟรมแรกสุด ตอนที่ยังไม่มีอะไรให้จำ

**2. ห้ามจับคู่กรวยที่อยู่คนละระยะ** — กรวยซ้ายใกล้ๆ จับคู่กับกรวยขวาไกลๆ ได้จุดกึ่งกลางที่เบี้ยว และแกว่งทุกครั้งที่กรวยไกลโผล่หรือหาย → คู่ที่ระยะต่างกันเกิน `max_pair_depth_diff_ratio` จะถูกปฏิเสธ ใช้อันที่ใกล้กว่าอันเดียว
"ระยะ" วัดจาก**ขอบล่างของกล่อง ไม่ใช่จุดศูนย์กลาง** เพราะฐานกรวยอยู่ติดพื้น จุดศูนย์กลางจะเลื่อนเวลากรวยโดนขอบเฟรมตัดด้วย ซึ่งไม่เกี่ยวกับระยะเลย

**3. เห็นข้างเดียวคือเรื่องปกติในโค้ง ไม่ใช่ error** — โค้ดเก่าเดาโดยใช้เศษส่วนของความกว้างเฟรม (`single_side_offset_ratio` ที่คอมเมนต์ในโค้ดเองยังบอกว่าเป็นค่าเดา)
ตัวนี้**จำความกว้างเลนจริงจากตอนที่เห็นครบสองข้าง** แล้วเอามาใช้ → เป็นค่าที่วัดได้ ไม่ใช่ค่าเดา (ค่าเดาใช้เฉพาะก่อนเห็นครบสองข้างครั้งแรก)

**4. ขอบกรวยขยับไปมาทุกเฟรมจาก JPEG noise** → เอาต์พุตผ่าน EMA ตั้ง `target_smoothing = 0` ถ้าอยากได้ค่าดิบ

### ค่าที่ปรับได้ (อยู่ใน `cone_config.json` ก้อนเดียวกัน)

| คีย์ | ความหมาย |
|---|---|
| `lane_half_width_ratio` | ครึ่งความกว้างเลนสำรอง ใช้ก่อนวัดค่าจริงได้ |
| `max_pair_depth_diff_ratio` | คู่กรวยที่ระยะต่างกันเกินนี้ = ไม่จับคู่ |
| `min_lane_gap_ratio` | ช่องว่างต้องกว้างอย่างน้อยเท่านี้ถึงจะนับว่าเป็น "เลน" ไม่ใช่กรวยแถวเดียว |
| `target_smoothing` | 0 = ดิบ, 0.9 = นิ่งมากแต่หน่วง |
| `lane_memory_frames` | หากรวยไม่เจอกี่เฟรมถึงจะทิ้งความจำ |
| `center_deadzone_px` | เบี่ยงน้อยกว่านี้ถือว่าตรงกลางแล้ว กันรถส่ายซ้ายขวา |

> transport แต่ยิง `/status` ไปถามบอร์ดตรงๆ: เฟิร์มแวร์หุ่นยนต์ตอบ `"robot":1` สเก็ตช์เดิมไม่มีฟิลด์นี้
> ถ้าไม่เจอ marker จะไม่ยอม arm (ดู `camera_control.is_robot_firmware()`)

```
python autodrive.py --dry-run                     # รันทั้ง loop ดูว่าจะสั่งอะไร แต่ไม่ส่งจริง
python autodrive.py --esp-ip 192.168.8.191        # ของจริง
python autodrive.py --esp-ip 192.168.8.191 --framesize svga --flip both
```

### ปุ่มต้องอ่านที่เดียว

ทั้ง `run.py` และ `autodrive.py` มีลูป 2 ทาง: ทางที่มีเฟรมใหม่ (`cv2.waitKey(1)`) กับทางที่ยังไม่มี (`cv2.waitKey(5)`)
**`waitKey` กินคีย์ที่กดไปไม่ว่าจะเรียกจากตรงไหน** ที่ 5 fps ทางว่างถูกเรียกบ่อยกว่าทางเฟรมใหม่ราว 25 เท่า
เมื่อก่อนตัวจัดการปุ่มอยู่แค่ทางเฟรมใหม่ ปุ่มที่กดเลยหายไปเกือบทั้งหมด — `v`/`h` เหมือนกดไม่ติด
และใน `autodrive.py` คือ SPACE ไม่ยอม arm กับ X ไม่ยอมหยุด ซึ่งอันตรายกว่ามาก

ตอนนี้ทั้งสองไฟล์รวมเป็น `handle_key()` ตัวเดียวและเรียกจากทั้งสองทาง วัดด้วยกล้องจำลอง 5 fps
กด `v` 20 ครั้ง: **ของเดิมทำงาน 0/20 ของใหม่ 20/20**

> ถ้าจะเพิ่มปุ่มใหม่ ใส่ใน `handle_key()` เท่านั้น อย่าเพิ่ม `cv2.waitKey` จุดที่สาม

### เชื่อมกล้องไม่ได้ / serial ขึ้น `[Power] Sensor Sleeping...`

**สองบรรทัดนี้ไม่ใช่ error**

- `E (...) task_wdt: TWDT already initialized` — Arduino core init watchdog ไว้ก่อนแล้ว
  `esp32cam_robot.ino:574` ดักไว้แล้วและเรียก `esp_task_wdt_reconfigure()` แทน ปล่อยผ่านได้
- `[Power] Sensor Sleeping...` — **ตั้งใจให้เป็นแบบนั้น** `cameraDrainTask` สั่งเซนเซอร์นอน
  จนกว่า `pcConnected` จะเป็นจริง ซึ่งเกิดเมื่อมีแพ็กเก็ต UDP อะไรก็ได้เข้าพอร์ต 44444
  คือกล้อง**กำลังรอ PC อยู่** ไม่ใช่กล้องพัง เฟิร์มแวร์จะ reboot เองทุก 120 วิถ้าไม่มี beacon (`BEACON_TIMEOUT`)

ให้ยิง beacon แล้วดูว่าอะไรตอบกลับ:

```
python esp32_link_check.py --esp-ip <ip ที่ serial พิมพ์>
```

มันฟังสองพอร์ตพร้อมกันเพื่อแยกสาเหตุที่ต้องแก้คนละทาง

| ผลที่ได้ | แปลว่า |
|---|---|
| ไม่มีอะไรกลับมาเลย | ESP ไม่ได้ยินเรา — IP ผิด, คนละเครือข่าย (ถ้าใช้ hotspot iPhone ต้องต่อ hotspot ตัวเดียวกันทั้งคู่), หรือ firewall บล็อกขาเข้าทั้งหมด |
| มี telemetry แต่ไม่มีวิดีโอ | ESP เห็นเราแล้ว แต่พอร์ต 44442 โดนบล็อกอย่างเดียว — เกือบทุกครั้งคือ Windows Firewall เพราะ telemetry กับวิดีโอมาคนละพอร์ต อนุญาตอันหนึ่งแต่ดรอปอีกอันได้ |
| มีวิดีโอ | ลิงก์ปกติ ไปรัน `run.py --source esp32 --esp-ip <ip>` ต่อได้เลย |

**ข้อควรระวังกับ hotspot ของ iPhone:** subnet เป็น `172.20.10.0/28` และ UDP broadcast มักไม่ทะลุ
ต้องใส่ `--esp-ip` ตรงๆ เสมอ อย่าพึ่ง broadcast discovery
และ Windows มักจัด hotspot เป็นเครือข่าย **Public** ซึ่งบล็อก UDP ขาเข้า ต้องอนุญาต python บนโปรไฟล์ Private

> `run.py` ค่าเริ่มต้นเป็น `--source webserver` ซึ่งสแกนหาพอร์ต 81
> **เฟิร์มแวร์หุ่นยนต์ไม่ได้เปิด HTTP เลย** จะหาไม่เจอตลอด ต้องใส่ `--source esp32` ด้วยทุกครั้ง

### เฟรมเรตของ `--source esp32` และวงจรอุบาทว์ที่เคยมี

`delivery:<pct>` ใน beacon คือครึ่งหนึ่งของ loop ปรับคุณภาพอัตโนมัติในเฟิร์มแวร์
(เพิ่มการบีบอัดเมื่อได้ค่าต่ำกว่า 50% ติดกัน 3 ครั้ง, ลดเมื่อเกิน 80% ติดกัน 5 ครั้ง)
เมื่อก่อน `esp32_video_source.py` **ส่งเลข `100` ตายตัวโดยไม่ได้วัดอะไรเลย**

บนลิงก์ที่แพ็กเก็ตหาย นั่นไม่ใช่การโกหกที่ไม่มีพิษภัย แต่เป็นสัญญาณที่**ชี้ผิดทาง**
เฟิร์มแวร์อ่านว่าลิงก์สมบูรณ์แบบ → ลดการบีบอัด → เฟรมใหญ่ขึ้น → ต้องใช้ chunk มากขึ้น →
หายมากขึ้น → แต่ PC ก็ยังรายงาน 100% อยู่ดี วัดจากของจริงบน hotspot iPhone: chunk หาย 22%,
เฟรมโตเป็น 32 chunk, ครึ่งหนึ่งมาไม่ครบ, ใช้ได้จริง **1.2 fps**

ตอนนี้วัดจริง: seq เป็นตัวนับเฟรม ช่องว่างระหว่างเฟรมที่มาครบสองเฟรมจึงเท่ากับจำนวนเฟรมที่หายพอดี
คิดเป็นสัดส่วนต่อหน้าต่าง beacon แล้ว EMA (ไม่ใช่เฉลี่ย `1/gap` ต่อเฟรม ซึ่งให้คะแนนลิงก์แย่สูงเกินจริง —
ช่องว่าง 1,1,2 เฉลี่ยได้ 83% ทั้งที่มาถึงจริงแค่ 3 ใน 4 เฟรม)

**ตัวรับตาบอดหลัง ESP รีบูต** เป็นอีกบั๊กที่เจอตอนไล่เรื่องนี้ เดิมกรอง seq ย้อนหลังด้วยหน้าต่าง 5000
พอบอร์ดรีบูต (ซึ่งมันทำเองทุก 120 วิถ้าไม่มี beacon) ตัวนับเฟรมเริ่มที่ 1 ใหม่ แต่ค่า high-water mark เดิมยังค้าง
เฟรมใหม่เลยถูกทิ้งทั้งหมดจนกว่าตัวนับจะไต่กลับไปถึงที่เดิม — ที่ไม่กี่ fps คือหลายนาทีที่ "ต่อติดแต่ไม่มีภาพ"
ตอนนี้ถอยหลังเกิน `REORDER_WINDOW` (30) ถือว่าบอร์ดรีบูต แล้ว resync ใหม่ทันที

### fps น้อย — วัดก่อนแก้

```
python run.py --esp-ip 192.168.8.191 --bench 10
```

ไม่เปิดหน้าต่าง ไม่ตรวจจับ วัดอย่างเดียวว่าเฟรมเข้ามากี่ fps / กี่ KB ต่อวินาที / เฟรมเฉลี่ยใหญ่แค่ไหน
มีไว้เพราะ "ภาพช้า" เกิดได้จากคนละสาเหตุและแก้คนละทาง

- **`--bench` ได้เลขสูง แต่หน้าต่างปกติช้า** → ปัญหาอยู่ที่ loop ฝั่ง PC
- **`--bench` ได้เลขต่ำเท่ากัน** → ปัญหาอยู่ที่กล้อง/WiFi จูนฝั่ง PC ยังไงก็ไม่ช่วย

ตัวเลขอ้างอิงที่วัดไว้บนเครื่องนี้: งาน CPU ต่อเฟรมของทั้งเส้นทาง (imdecode + detect + วาด) ที่ VGA
รวมกันราว **6 ms** และตัวรับ MJPEG เดี่ยวๆ ทำได้ระดับพันกว่า fps เมื่อยิงจาก server ในเครื่อง
ทั้ง loop พร้อมหน้าต่าง 2 บาน เพดานอยู่ที่ **~120 fps** — ถ้าของจริงได้เลขหลักเดียว แปลว่าคอขวดคือลิงก์ ไม่ใช่ Python

### ภาพกระตุกเป็นบางครั้ง และแย่ลงเรื่อยๆ ถ้าเปิดทิ้งไว้นาน

`--bench` วัดครั้งเดียวบอกไม่ได้ว่าอะไร "ค่อยๆ แย่ลง" ต้องดู**แนวโน้ม**ของหลายตัวเลขพร้อมกันเป็นสิบๆ นาที:

```
python link_monitor.py --esp-ip 192.168.8.191                # 20 นาที แถวละ 10 วิ
python link_monitor.py --esp-ip 192.168.8.191 --minutes 40 --quality 16 --ae-level -1
```

เปิดสตรีมเหมือน `run.py` ทุกอย่าง แล้วพิมพ์ทุก 10 วิ: fps / KB/s / KB ต่อเฟรม / ระยะห่างระหว่างเฟรม (p50, p95, แย่สุด)
/ ping ไปบอร์ด / และสิ่งที่บอร์ดรายงานเองผ่าน `/status` (RSSI, heap, อุณหภูมิชิป, uptime) เขียน CSV ไว้ด้วย
จบแล้วเทียบช่วงต้นกับช่วงท้ายและสรุปให้ว่าตัวไหนขยับ:

| แนวโน้ม | สาเหตุ | ทางแก้ |
|---|---|---|
| **KB/เฟรมโตขึ้น** แต่ KB/s เท่าเดิม | เซ็นเซอร์ร้อน → noise มากขึ้น → JPEG ใหญ่ขึ้น ลิงก์ที่รับได้เท่าเดิมเลยส่งได้น้อยเฟรมลง | `--quality 16–20`, ระบายความร้อน/บังแดด, ลด XCLK |
| **KB/s ตก** แต่ KB/เฟรมเท่าเดิม, ping แย่ลง | วิทยุส่งได้น้อยลง — ESP32 ร้อนที่ TX 19.5 dBm, ไฟตก | จัมเปอร์เสาอากาศ, ไฟ 5V ≥ 1A สายสั้น, ระยะ, ช่อง 2.4 GHz |
| `heap largest` หดลงเรื่อยๆ | heap เฟิร์มแวร์แตกกระจาย จะค้าง/รีบูตในที่สุด | บั๊กเฟิร์มแวร์ ต้องไล่ |
| `uptime` ย้อนกลับ | บอร์ดรีบูต | ไฟเลี้ยงก่อนอย่างอื่น |
| gap p95 กว้างขึ้นอย่างเดียว ตัวอื่นนิ่ง | ฝั่ง PC | ดู Task Manager, power saving ของ WiFi adapter |

ใส่ `--detect` (และ `--show` ถ้าอยากรวมค่าใช้จ่ายของหน้าต่างด้วย) จะรันตรวจจับกรวยบนทุกเฟรมเหมือน `run.py --detect`
แล้วเพิ่มคอลัมน์ `proc` (fps ที่ประมวลผลทัน) กับ `det ms` (เวลาต่อเฟรม) — วัดจริง 2026-09-14 บน hotspot: รับ 13–14 fps
ประมวลผลได้ 13–14 fps เท่ากัน detect **3 ms/เฟรม** (ช่วงเฟรม ~70 ms) แปลว่า `--detect` ไม่ได้ทำให้ภาพช้าลงเลย

ค่า heap/อุณหภูมิ/uptime ต้องใช้เฟิร์มแวร์ `firmware/esp32cam_robot/` รุ่นปัจจุบัน (เพิ่มลง `/status` แล้ว) บอร์ดที่ยังไม่ได้แฟลชใหม่จะขึ้น `-` แต่ที่เหลือใช้ได้

ที่ตรวจแล้วว่า**ไม่ใช่**ตัว drift: ตัวรับ MJPEG ฝั่ง PC ยิงจาก server ในเครื่อง 3 นาที latency 2.5 ms และ RSS ~57 MB นิ่งตลอด

### ปุ่มที่มีผลกับ fps มากที่สุด

| ปุ่ม | ทำอะไร |
|---|---|
| `--quality 16` | JPEG quality 10 (ดีสุด/ใหญ่สุด) .. 63 (แย่สุด/เล็กสุด) **`CameraWebServer` บูตมาที่ 10 คือใหญ่ที่สุดเท่าที่ทำได้** ขยับเป็น 16–18 ลดขนาดเฟรมเกือบครึ่ง แต่ detector ที่ดูก้อนสีฟ้าแทบไม่รู้สึก |
| `--framesize qvga` | เล็กลง 4 เท่า เร็วขึ้นมาก แต่**ต้องจูน `min_contour_area` ใหม่** เพราะเป็นพิกเซลดิบ ใช้ได้กับ `--source esp32` ด้วยแล้ว (ส่งเป็นคำสั่ง UDP) วัดจริงบน hotspot: VGA 1.2 fps → QVGA **7.6 fps** |
| `--ae-level -1` | เอนไปทางมืด = ชัตเตอร์สั้น ในห้องแสงน้อย AEC จะเลือกชัตเตอร์ยาวจนเกินคาบเฟรม แล้ว OV2640 จะแทรก dummy line ทำให้ **fps ของตัวเซนเซอร์เองตก** โดยที่ WiFi ยังว่างอยู่ ลดภาพเบลอตอนรถวิ่งด้วย (เฟิร์มแวร์หุ่นยนต์ตั้ง `-1` ไว้ด้วยเหตุผลเดียวกัน) |

`--ae-level` ต้องสั่ง**ก่อน**ล็อก AEC ไม่งั้นค่าจะโดนแช่ไปแล้วและไม่มีผล — `prepare_camera()` เรียงลำดับให้แล้ว
ทั้งสามปุ่มใช้ได้เฉพาะ `--source webserver` ส่วนเฟิร์มแวร์หุ่นยนต์ผูก quality ไว้กับ preset ของความละเอียดในตัว `.ino` เอง

### ภาพของ `autodrive.py` ต้องชัดเท่า `run.py`

ทั้งสองไฟล์เรียก `camera_setup.prepare_camera()` ตัวเดียวกัน ทำ 3 อย่างก่อนเปิดสตรีม
คือ **ตั้งความละเอียด (ค่าเริ่มต้น VGA)**, **ล็อก AWB/AEC/AGC**, และ **สั่ง flip**
ต้องทำก่อนเปิดสตรีมเสมอ เพราะกล้องรับ client ได้ทีละตัว `/capture` ที่ใช้ยืนยันว่าความละเอียดเปลี่ยนจริง
จะแย่งช่องกับ MJPEG stream ไม่ได้

เคยมีบั๊กตรงนี้: `autodrive.py` รุ่นก่อนข้ามขั้นตอนนี้ทั้งหมด แล้ว `CameraWebServer.ino`
**บูตมาที่ QVGA 320×240** และอยู่อย่างนั้นถ้าไม่มีใครสั่ง ภาพเลยเบลอกว่า `run.py` ทั้งที่โค้ดรับภาพเป็นไฟล์เดียวกัน
ซ้ำร้ายคือ `min_contour_area` เป็นพิกเซลดิบ พอเฟรมเล็กลง 4 เท่าก็ตรวจไม่เจอกรวยด้วย

`--source esp32` ต่างออกไป: เฟิร์มแวร์หุ่นยนต์ไม่มี HTTP endpoint เลย
ความละเอียดจึงส่งเป็นคำสั่ง UDP (`RobotLink.set_framesize()` → cmd 4/5/6/7) แทน
และ **ล็อก AWB จากฝั่ง PC ไม่ได้** เพราะ `updateCameraSettings()` ใน `.ino` เปิด `set_whitebal`/`set_awb_gain` ใหม่ทุกครั้ง
โหมด `--dry-run` ไม่มี link เลยสั่งความละเอียดไม่ได้ ปล่อยตามค่าที่เฟิร์มแวร์บูตมา (VGA q12)

| ปุ่ม | ทำอะไร |
|---|---|
| `SPACE` | arm / disarm |
| `X` | หยุดฉุกเฉิน (disarm + ส่ง neutral) |
| `Q` | ออก (หยุดรถก่อนออก) |
| `W` | บันทึกค่าที่จูน |

**โปรแกรมเริ่มมาแบบ DISARMED เสมอ** เปิดมาแล้วรถจะไม่วิ่งเอง ต้องกด SPACE
ตอน disarm ยังคำนวณและโชว์ค่าที่ *จะ* สั่งอยู่ ใช้ดูว่า gain โอเคไหมก่อนปล่อยจริงได้
ตอน armed ขอบจอเป็นกรอบแดง มองจากไกลๆ ก็รู้

### ชั้นความปลอดภัย 5 ชั้น

1. เริ่มมา disarmed ต้องกดเองถึงจะขยับ
2. หยุดฉุกเฉินที่ `X`, `Q`, ปิดหน้าต่าง และใน `finally` ของ main loop — **รวมถึงตอนโค้ดพัง exception** ด้วย โค้ด vision พังต้องไม่ทิ้งคันเร่งค้างไว้
3. **ภาพค้าง = หยุด** ถ้าเฟรมไม่มาเกิน `--stale-timeout` (ค่าเริ่ม 1 วิ) จะหยุดและ disarm ทันที เพราะรถที่วิ่งตามภาพแช่แข็งอันตรายกว่ารถที่ไม่วิ่ง
4. หากรวยไม่เจอเกิน `stop_after_lost_frames` → หยุด และ**ตัดพวงมาลัยเป็น 0 ด้วย** (ค้างมุมเลี้ยวไว้ตอนตาบอด = ขับเป็นวงออกนอกลู่)
5. เฟิร์มแวร์ตัดมอเตอร์เองถ้าไม่ได้รับแพ็กเก็ตเกิน 150 ms

ชั้นที่ 5 เป็นชั้นเดียวที่รอดตอนคอมดับ อีก 4 ชั้นถือเป็นความสะดวก — **รอบแรกๆ เอามือไว้ใกล้สวิตช์ปิดรถด้วย**

### ตัวคุม (P อย่างเดียว)

ไม่ใส่ I และ D ตั้งใจ — ระบบนี้หน่วงเยอะ (WiFi + JPEG + decode รวมกัน ~150 ms) ตัว I จะสะสมแล้วแกว่ง
ส่วน D จะไปขยาย noise รายเฟรมที่ `lane_center` เพิ่งกรองออกไป **ถ้ารถส่ายให้ลด `steer_gain` ก่อน อย่าเพิ่งเติมเทอม**

3 อย่างที่ไม่มีใน P-controller ตำราแต่จำเป็นที่นี่

1. **โค้งแล้วช้าลง** — คันเร่งลดตาม `|steer|` รถที่เข้าโค้งด้วยความเร็วทางตรงจะดริฟท์ออกนอก แล้วหลุดกรวยฝั่งใน = ไม่เหลืออะไรให้เลี้ยวตาม
2. **ค่อยๆ เร่ง อย่ากระชาก** — คันเร่งไต่ขึ้นแบบจำกัดอัตรา กระชากจาก 0 เต็มที่ทำให้รถสะดุดและภาพเบลอ ซึ่งเป็นจังหวะที่ตัวตรวจจับต้องการภาพชัดที่สุดพอดี **แต่ตอนเบรกไม่ไต่ ลดทันที**
3. **หลงทางแล้วหยุด** ไม่ใช่ "วิ่งต่อด้วยมุมเลี้ยวเดิม"

| คีย์ | ค่าเริ่ม | ความหมาย |
|---|---|---|
| `steer_gain` | 0.8 | เริ่มต่ำไว้ก่อน สูงไปจะดูเหมือนดีบนทางตรงแล้วไปแกว่งตอนแก้โค้งครั้งแรก |
| `base_throttle` | 0.35 | ความเร็วบนทางตรง ช้าดีบั๊กง่ายกว่าเร็ว |
| `turn_slowdown` | 0.5 | ความเร็วตอนเลี้ยวสุด (เท่าตัวคูณ) |
| `throttle_ramp_per_s` | 1.0 | เร่งได้เร็วแค่ไหนต่อวินาที |
| `stop_after_lost_frames` | 5 | หากรวยไม่เจอกี่เฟรมถึงหยุด |
| `one_side_throttle_scale` | 0.7 | เห็นข้างเดียว = เป้าเป็นค่าอนุมาน ลดความเร็วลง |

### วิธีส่งภาพ: MJPEG เป็นหลัก UDP เป็นตัวสำรอง

เดิมเฟิร์มแวร์หุ่นยนต์ส่งภาพทาง UDP อย่างเดียว — หั่น JPEG เป็นชิ้นละ 1400 ไบต์ ยิงออกไปโดย
ไม่มีการส่งซ้ำ **หายชิ้นเดียวก็เสียทั้งเฟรม** เพราะ `esp32_video_source.py` ต้องได้ครบทุก chunk
ถึงจะ decode ตอนนี้ default เปลี่ยนเป็น **MJPEG over HTTP พอร์ต 81** แบบเดียวกับ `CameraWebServer`
เป๊ะๆ — TCP ส่งซ้ำให้ ภาพจึงมาครบถ้วนตรงไบต์เสมอ ไม่ก็ค้างไปเลย ไม่มีสภาพครึ่งๆ กลางๆ

เฟิร์มแวร์เปิด httpd **สองตัวแยกกัน** เหมือนสเก็ตช์เดิม: พอร์ต 80 (`/control`, `/status`,
`/capture`) กับพอร์ต 81 (`/stream`) แยกกันเพราะ handler ของ `/stream` ไม่มีวัน return
ตราบใดที่ยังมี client อยู่ ถ้าอยู่ตัวเดียวกันจะบล็อก `/status` ไปด้วย

เส้นทาง UDP ยังอยู่ครบ เก็บไว้เพราะเป็นทางเดียวที่ค้นหา PC เองได้โดยไม่ต้องรู้ IP ก่อน สลับด้วย:

```
python -c "import camera_control as c; c._set_var('192.168.8.191','video_mode',1)"   # -> UDP
python -c "import camera_control as c; c._set_var('192.168.8.191','video_mode',0)"   # -> MJPEG
```

หรือส่ง UDP cmd `9` (ไป UDP) / `8` (กลับ MJPEG) ทาง `robot_link`

**สองอย่างที่ต้องรู้:**

- ตอนอยู่โหมด MJPEG `cameraDrainTask` กับ `streamTXTask` จะนอน 100 ms วนไปเฉยๆ ไม่แตะกล้องเลย
  ถ้าปล่อยให้แย่ง `esp_camera_fb_get()` กับ handler ของ `/stream` จะชนกันที่ frame buffer แค่ 2 ตัว
  และเผา core 0 ซึ่งเป็น core ที่ WiFi อยู่ ทิ้งเปล่า
- **adaptive quality loop ทำงานเฉพาะโหมด UDP** เพราะบน TCP ฝั่ง PC จะวัด delivery ได้ ~100% เสมอ
  ปล่อยไว้มันจะไล่ `current_quality` ลงไปถึง 10 = เฟรมใหญ่ที่สุดที่เซนเซอร์ทำได้ ยัดให้วิทยุจนไม่ไหว

### โปรโตคอลควบคุม

`robot_link.py` แกะมาจาก `../Aj-Piya_code/2026_07_13.py` เอาเฉพาะส่วนส่ง — UDP text `seq,cmd,v1,v2` ไปพอร์ต 44441

- `ev()` แปลง -1..1 → 1000..2000 µs (1500 = นิ่ง) เฟิร์มแวร์คูณ `MAX_DUTY` 3.27675 เป็น PWM 16-bit ที่ 50 Hz
- คำสั่งซ้ำจะไม่ส่ง แต่**ส่งซ้ำทุก 50 ms อยู่ดี** เพราะเฟิร์มแวร์ตัดมอเตอร์ที่ 150 ms
- ตัวส่งจะยุบ drive packet ในแบตช์เหลืออันใหม่สุด — ส่งคิวมุมเลี้ยวเก่าค้างไปคือให้รถไล่ตำแหน่งที่มันผ่านไปแล้ว
- คำสั่ง `8` / `9` สลับวิธีส่งภาพ (MJPEG / UDP) — ใช้ checksum แบบเดียวกับ `3`–`7` คือ `v1`/`v2` ต้องเท่ากับเลขคำสั่ง
- **`stop()` ข้ามคิวไปส่งตรงเลย** และล้างคิวทิ้งก่อน ไม่งั้นการยุบแบตช์จะกลืน burst หายไป และคำสั่งเก่าที่ค้างคิวอาจถูกส่งตาม *หลัง* คำสั่งหยุด
